# Developer Guide

How to make the repository work just after `git clone`.

```sh
git clone git@github.com:stopsopa/xx.git
cd xx
```

## Local Toolchain Setup

### Install Rust

```sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
```

### Add the macOS arm64 target

```sh
rustup target add aarch64-apple-darwin
```

(on other machines `bash/detect_arch.sh` picks the target, see the `TARGET` variable there)

### Other tools

- **node 22.18+** - the `xx` binary runs `node` to load the config, so it is needed to use `xx` and to run the tests. Tests load `xx.ts`, that is where the minimal version comes from (node strips types on its own since 22.18). Also `tag.sh` uses it for the patch / minor / major picker (`bash/file/fuzzy.ts`).
- **zsh** - tests run the wrapper in bash and in zsh.
- **python3** - only `test/test018` (creates a pseudo terminal to press real Ctrl+C).
- **npm** - `npm ci` installs esbuild (the only dependency, `package.json`), used by `transpile.sh` to generate the templates. `test.sh` needs it.
- **curl** or **wget** - `xx --init` downloads the template with it (tests don't, they use local files).

### Verify toolchain

Run the validation script to confirm everything is in order:

```sh
/bin/bash validateenv.sh
```

Exit 0 means the local toolchain is ready for development.

## Build locally

```sh
/bin/bash compile.sh
```

Result, version inside of both is `dev`:

- `bin/<arch>/xx` - the binary (`bin/arm64/xx` or `bin/x64/xx`)
- `bin/<arch>/xx.sh` - the wrapper generated for exactly that binary (md5 of the binary embedded, see "Contract" below). It is regenerated by every `compile.sh`.

On stdout `compile.sh` prints only absolute paths of all binaries found in `bin/` after the build, one per line. Everything else goes to stderr:

```sh
/bin/bash compile.sh 2> /dev/null
# /path/to/clone/bin/arm64/xx
```

## Use the local build

Nothing is searched automatically, three lines are needed. The alias points to the **generated** wrapper in `bin/`, not to `xx.sh` in the root of the repository (that one has no md5 embedded and refuses to work):

```sh
# ~/.bashrc or ~/.zshrc
export XX_BIN="/path/to/clone/bin/arm64/xx"
export XX_NODE_BINARY="/path/to/node"       # node -e 'console.log(process.execPath)'
alias xx='source "/path/to/clone/bin/arm64/xx.sh"'
```

`~/` at the beginning of `XX_BIN` and `XX_NODE_BINARY` is expanded by `xx.sh` and by the binary (`locate::expand_tilde`), also when written in quotes.

After changing `xx.sh` or anything in `src/` run `compile.sh` again, it refreshes both files.

To try it next to the old `xx` without replacing it, give the alias another name (`alias xxn=...`).

This repository has its own `xx.ts`, so inside of the clone `xx` shows: `help`, `validateenv`, `compile`, `test`, `release notes preview`, `publish`.

## Running Tests Locally

```sh
npm ci                    # once
/bin/bash compile.sh
/bin/bash test.sh
```

`test.sh` first generates the templates (`transpile.sh`), then runs:

1. `cargo test` - unit tests of pure logic (sorting, `<% name %>`, lookup of the config, menu rows, shape of node version).
2. every `test/test*/test.sh` - end to end tests of the compiled binary and of `xx.sh`. Each directory has `EXPLANATION.md` saying what the test proves.

One test alone:

```sh
/bin/bash test/test006/test.sh
```

Things worth knowing when writing a test:

- Start with the two lines every test starts with (`DIR=...` and `source "${DIR}/../_lib.sh"`). `test/_lib.sh` gives the test an empty temporary directory as `pwd`, another one as `HOME` and another as `XX_TMP`, because result of `xx` depends on `pwd`, on `.git`, on `~/xx.*` and scripts without `.git` go to `XX_TMP`. It also sets `XX_BIN` and `XX_NODE_BINARY` (resolved from `node` in `PATH` unless you set it yourself) and unsets `NODE_OPTIONS` and the rest of `XX_*`.
- `write_config` and `check_config` from `test/_lib.sh` create a config of given flavour (`ts`, `esm`, `cjs`) and check that it is listed, generated and executed (see `test/test019`).
- `xx --init` in tests never touches the network: `XX_INIT_CONFIG` points to a local json with local paths (see `test/test016`).
- The menu is driven without a terminal: `XX_TEST_KEYS="down,down,enter"` (list of keys in `src/menu.rs`, struct `Scripted`). What would be drawn goes to stderr. `XX_TEST_SIZE="60x20"` sets size of the "terminal".
- Real terminal behaviour (Ctrl+C, escape sequences of arrow keys) is tested only in `test/test018` through `terminal.py`. It waits for prompts and expected text, never for a fixed time; keep it that way, fixed sleeps made this test take 15 seconds.

## Layout

```
src/main.rs        arguments, exit codes, --help --version --list --init --esm --gen, main flow
src/locate.rs      where is the config, where to write the generated script
src/node.rs        XX_NODE_BINARY check, XX_NODE_OPTIONS
src/loader.rs      runs node with loader.js, reads list of commands
src/loader.js      executed by node: imports the config, prints commands as json
src/model.rs       Command, validation, <% name %>, sorting, pick by name / number
src/menu.rs        menu and "Run command?" question, real terminal and scripted one
src/range.rs       block indicator in front of menu rows
build.rs           version: XX_VERSION env, otherwise "dev"
xx.sh              source of the wrapper (sourced by the alias, executes the generated script)
init.json          default XX_INIT_CONFIG: where xx --init finds templates (GitHub Pages are the source of truth)
templates/         xx.ts, the template downloaded by xx --init (xx.js xx.mjs xx.cjs are generated, not committed)
transpile.sh       generates templates/xx.js xx.mjs xx.cjs from templates/xx.ts (esbuild, bash/transpile.mjs)
package.json       only dev dependency: esbuild
xx.ts              xx menu of this repository
bash/              detect_arch.sh, embed.sh (md5 + version into xx.sh), release_notes.sh, file/fuzzy.ts
test/              end to end tests
```

## Contract between `xx.sh` and the binary

Described at the top of `src/main.rs` and `xx.sh`, covered by `test/test017` and `test/test023`:

- **md5**: `xx.sh` computes md5 of the file from `XX_BIN` before every use (`md5sum`, or `md5` on macOS) and continues only if the hash is on the list embedded in `xx.sh` itself (`__XX_BIN_MD5`). Anything else (other program, other version, rebuilt or modified binary) is refused; the error shows both hashes plus version of `xx.sh` and the answer of the file to `--version`.
- **Embedding** is done by `bash/embed.sh <version> <output xx.sh> <binary>...`: it copies `xx.sh` from the repository replacing two lines, `__XX_VERSION="dev"` and `__XX_BIN_MD5=""`. Don't reformat those lines, `embed.sh` and `test/test017` fail when they are not found exactly once. `compile.sh` embeds the hash of the one binary it built, the release workflow embeds hashes of binaries of all platforms into the single `xx.sh` of the release.
- **`xx.sh` in the repository** has the list empty and refuses to work, so a wrapper is never used with a binary it was not built with.
- **Exit codes** of the binary tell `xx.sh` what to do with the generated script: `0` run with `/bin/bash`, `55` source, `10` not confirmed, `130` cancelled, anything else is an error.

## Release and Publishing Process

### CI/CD Workflow Overview

There is one workflow, `.github/workflows/rust.yml`, so one push gives one run. What it does depends on what was pushed:

| Pushed | Jobs |
| --- | --- |
| any branch, any PR | `test` → `build-matrix` (tests on Linux x64, then binaries for all platforms to prove they build) |
| `main` | the same, and after `test` passes: `pages-build` → `pages-deploy` (GitHub Pages) |
| a tag | the same as any branch, and after `build-matrix`: `release` (GitHub Release) |

- Nothing is published when tests fail: neither Pages nor a release.
- Jobs which don't apply are shown as skipped in the run.
- Commit with `[no ci]` in the message doesn't trigger the pipeline.
- Actions → "CI, Release & Pages" → Run workflow starts it by hand (on `main` it republishes Pages).

### Target Platforms Built in CI/CD
- **macOS arm64** (`aarch64-apple-darwin` → `xx-darwin-arm64`)
- **Linux x64** (`x86_64-unknown-linux-gnu` → `xx-linux-x64`)
- **Linux arm64** (`aarch64-unknown-linux-gnu` → `xx-linux-arm64`)

Every release also contains one `xx.sh` with the tag and md5 of all three binaries embedded (the binary alone is not usable, and `xx.sh` refuses any binary which is not from its release) and `SHA256SUMS.txt` covering the binaries and `xx.sh`.

## Creating a Release

1. Add section `## vX.Y.Z` for the new version to `changelog.md` and commit it. The release workflow copies that section to the top of the release page. Without the section the release page has only the installation part.

2. Preview the release page if you like (prints markdown):

   ```sh
   /bin/bash bash/release_notes.sh v1.0.0 stopsopa/xx <directory with SHA256SUMS.txt>
   # or simply, from the xx menu of this repository:
   xx "release notes preview" v1.0.0
   ```

3. Use the helper script `tag.sh` to bump version and push tag. A release is created only this way, by a pushed tag:

   ```sh
   /bin/bash tag.sh patch   # or minor, major
   ```

   It takes the highest existing `vX.Y.Z` tag and increments it according to semver: `patch` x.y.Z+1, `minor` x.Y+1.0, `major` X+1.0.0. Without any tag it starts from `0.0.0`, so the very first release is `v0.0.1` (patch), `v0.1.0` (minor) or `v1.0.0` (major).

   Before asking for confirmation it warns when: there are uncommitted changes (they will not be in the release), current commit is not pushed, `changelog.md` has no section for the new tag. If pushing the tag fails the local tag is removed, so the next run doesn't skip a version.

Example session:
```text
Fetching git tags...

Previous tag: v0.0.4
Mode:         patch
New tag:      v0.0.5

Press Enter to create and push tag 'v0.0.5', or Ctrl+C to abort...
Enumerating objects: 9, done.
...
To github.com:stopsopa/xx.git
 * [new tag]         v0.0.5 -> v0.0.5
Successfully created and pushed tag >v0.0.5<
```

### What happens next

1. GitHub Actions detects the tag push and runs the pipeline.
2. It compiles binaries for macOS arm64, Linux x64, and Linux arm64. The tag is embedded as the version (`xx --version`).
3. Generates `xx.sh` with the tag and md5 of the binaries embedded (`bash/embed.sh`), computes SHA-256 hashes for all files and generates the release notes with `bash/release_notes.sh`: section from `changelog.md`, then `curl`, `wget`, and verification commands for each platform (always for two files: the binary and `xx.sh`, downloaded to the current directory). `README.md` → Installation → step 2 continues from there.
4. Creates and publishes the GitHub Release with attached platform binaries, `xx.sh` and `SHA256SUMS.txt`.

After the first release check that `README.md` → Installation still matches what the release page says.

## GitHub Pages

Jobs `pages-build` and `pages-deploy` of `.github/workflows/rust.yml` publish the root directory of the repository to https://stopsopa.github.io/xx/ on every push to `main`, after the tests passed (and on demand: Actions → CI, Release & Pages → Run workflow). Before that it runs `transpile.sh`, so `templates/xx.js`, `xx.mjs` and `xx.cjs` are published too. The rest of the files are copied as they are, without `.git`, `.github`, `target`, `bin`, `node_modules`, `vendor` and `__links`.

One time setup: repository **Settings → Pages → Build and deployment → Source: GitHub Actions**. Until that is switched on the workflow fails on the deploy step.

There is no `index.html` in the repository, so the root address shows 404, files are reachable by their paths, e.g. `https://stopsopa.github.io/xx/templates/xx.ts`.

## Templates for `xx --init`

Only `templates/xx.ts` is maintained by hand and committed. `templates/xx.js`, `templates/xx.mjs` and `templates/xx.cjs` are generated from it and ignored by git:

```sh
npm ci                      # once, installs esbuild
/bin/bash transpile.sh      # prints paths of the three generated files
```

`transpile.sh` (the work is done in `bash/transpile.mjs`):

- esbuild removes the types; `export default` stays for `xx.js` / `xx.mjs` and becomes `module.exports =` for `xx.cjs`.
- esbuild also removes comments, so the comment at the top of `xx.ts` is carried over by hand: its first paragraph describes `xx.ts` itself and is replaced with a description of the generated flavour, the rest is copied. Comments further down in the code are not in the generated files. Text inside of the shell scripts (template literals) is untouched.
- at the end every generated file is loaded and has to return exactly the same commands as `xx.ts`, otherwise the script fails.
- `xx.ts` has to keep exactly one export: `export default <function>`.

Who runs it:

- job `pages-build` of `.github/workflows/rust.yml` just before publishing, so the generated files exist only on GitHub Pages.
- `test.sh` at the start, `test/test016` uses the generated files (it also fails if one of them gets committed).

`xx --init [ts|js|mjs|cjs]` first downloads `init.json` (`https://stopsopa.github.io/xx/init.json`, can be replaced with `XX_INIT_CONFIG`), then the template listed there under the requested key (`https://stopsopa.github.io/xx/templates/xx.<kind>`). Nothing is embedded in the binary, so changing the template means only: edit `templates/xx.ts`, push to `main`, the Pages workflow publishes all four. No release needed. GitHub Pages can serve the old version for a few minutes after the deployment.
